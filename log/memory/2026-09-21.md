### 环境问题：这台机器无法用 git 访问 GitHub

### 推送前先比对远程 HEAD —— 这次真的救了数据
- 本地记录的 `origin/main` 停在 `f88efe9`，但远程实际已经是 **`6c13c44`**（"Enhance README with detailed project information"），是温琼林通过 **GitHub 网页端**直接改的中英双语 README 概览。

### 复现远程提交：签名挡住了，但 payload 给了答案
- `6c13c44` 是 **GitHub 官方 PGP 签名**的提交（`verification.verified: true`），签名无法伪造，靠重放元数据复现必然失败（SHA 差在 `gpgsig` 头，且 API 把日期归一化成 UTC，掩盖了真实的 `+0800`）。
- 但 `GET /git/commits/{sha}` 返回的 `verification.payload`（签名覆盖的原文）与 `verification.signature` 都是公开数据，于是**逐字节还原提交对象**再用 `git hash-object -t commit -w --stdin` 写回本地对象库，SHA 精确命中。
- gpgsig 的折行规则：`"gpgsig " + signature.replace("\n", "\n ")`，再接 `"\n\n"` 与消息。

### 推送方式：走 REST API 搬运 git 对象
写了 `_push_api.cjs`（**未纳入版本库**）：上传缺失 blob → 用 `base_tree` 建树 → 建提交 → 更新引用，**每一步都校验返回的 sha 与本地完全一致，全部通过才动引用**，因此本地与远程不会分叉。空跑用 `DRY=1`。
- 踩坑：curl 配置文件（`curl -K -`）里的字符串会处理**反斜杠转义**，Windows 临时路径必须转成正斜杠，否则输出文件被写到别处（还会在项目里留下 `Userslenovo...` 这种怪文件名）。
- 令牌用 GCM 从 Windows 凭据管理器读取（`git-credential-manager get`）；WorkBuddy 自带的 PortableGit 的 exec-path 里**没有**凭据助手，得用系统装的 Git for Windows 那个。

### README 的处理
没有用我的版本覆盖网页端那版，而是**保留它的双语结构、更新过期数据**：23→32 项测试、5→15 关、par 40–76→40–96、BFS→A\*、目录表补齐 `screenshots.cjs` 与截图，并补上「设计说明」一节。

### 沙箱遗留（不影响远程）
- 沙箱会**阻止创建** `.git/refs/remotes/origin/`（`mkdir` 成功但目录随即消失），所以本地 `origin/main` 跟踪引用建不起来，`git status` 会显示 `main...origin/main [gone]`。
- 远程本身是正确的；在你自己终端里 `git fetch` 一次即可恢复。

## 第七轮：按《评审与优化方案》整改（P0 → P1 → P2）

用户给了 `星核迷航_评审与优化方案.docx`，要求照着改。方案分了三个阶段，这轮全部走完。

### 先复现数据，才发现方案自己也漏了一条
- 写 `tests/optimal-levels.cjs`，把关卡结构解析搬到 Node 侧、每关求**精确最优解**（不带任何启发式高估）。20/20 复现出了评审给的数据。
- **顺手挖出评审没发现的问题**：游戏内的 `planRoute` 提示用的是「刻意高估」的启发式，在 20 关里有 **10 关给出的路线比最优长 10–43%**（第 17 关：43 步 vs 最优 30 步）。而评审建议把 `par` 从平均高 31.75 步收紧到约 1.3 倍最优——**照这个建议改完，跟着提示走反而会掉到二星**。所以必须先修求解器，再动 `par`，否则是把一个坑换成另一个坑。

### 求解器：从「刻意高估」换成「可采纳 MST 启发式」
- `planHeuristic(st)` = 对「剩余星核 + 出口」求 Prim 最小生成树；两点距离来自 `staticDist(level,ax,ay,bx,by)`，后者由 `buildDistTable(level)` 惰性建一次全局 BFS 距离表并缓存在 `distTables` Map 里（超 8 条就清空，避免 20 关 × 117² 一直占着）。
- 因为永不高估，A\* 返回的就是**真正最短的无伤路线**；实测比旧启发式快 **10–37 倍**（旧版在高估方向上是「更省搜索但答错」，新版是「答对且更快」，没有取舍）。
- 回到 README 的取舍段落时不要忘了：那段「刻意高估是实测后的取舍」的说明**已经不成立**，已改写。

### P0（两个真 bug）
1. **`pathFirstStep` 起点=终点时死循环**：`while(prev.get(k)!==startK)k=prev.get(k)` 在起点即终点时取到 `undefined` 并永远循环，页面直接卡死（会被守卫的 BFS 追路撞上）。加 `if(goalK===startK)return null;` 提前返回。
2. **撞暗影兽后每一步都在掉血**：兽被撞退后回到巢穴，而巢穴正是玩家脚下，于是 `step()` 里「玩家走进兽格」的分支每回合都命中，6 步内必死且**画面上完全看不出来**（精灵被玩家挡住，气泡还写着「它退回巢穴」）。修了三处才干净：① 新增 `rehomeMonster()`，退回巢穴**或**巢穴旁的空格，总之不在玩家脚下；② 兽加 `refit` 状态，重整 1 回合内既不移动也不造成伤害；③ `step()` 的玩家撞兽分支加 `!m.refit`卫。诊断靠 `sc-diag2.cjs` 跑纯 `step()` 轨迹才定位到——看动画是找不到的。

### P1（核心设计）
- **单回合伤害上限**：新增 `takeDamage(s,events,guard,source)`，一个 `{used:false}` 的 guard 走完整个回合，**无论激光+兽、守卫+守卫叠了多少次，最多只掉 1 格护盾**。评审指出旧版会出现「画面上只挨了一下、实际掉 2 血」。测试对 20 张地图 × 所有可站立格 × 4 个方向**穷举**，断言没有任何组合单回合掉 >1。
- **实体互斥占位**：`stepMonsters` 里加 `free(point,self)`，兽与守卫不再叠在同一格（第 20 关第 11 步两名守卫会重叠到 (7,6)，看着一个、撞上去掉 2 血）。
- **激光对称规则**：`onActiveLaser(s,x,y)` —— 站在开启的激光上，**玩家和守卫都掉血**。守卫「被引到激光上」这件事从此是规则而非彩蛋。
- **目标步数收紧**：`[30,35,40,50,40,35,40,35,50,50,35,40,55,35,40,35,40,40,50,40]`（≈ 最优 × 1.3–1.48，原先是 1.82–3.56 倍）。`OPTIMAL_STEPS` 写进页面当「尺子」。
- **「贴地飞行」徽章**：原本要求「不超过 par 的一半」，但 par 收紧后其中一关（L1）**已经不可能达成**。用户拍板改成「最优 × 1.15 三星通关」——20/20 可达，而且成了三星之上的真挑战（不再与 par 耦合）。
